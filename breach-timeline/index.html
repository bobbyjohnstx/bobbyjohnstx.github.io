SSRF and Internet Access

⚠ What happened

■ Red Hat defense
OpenShift OVN-Kubernetes Requires config

Red Hat OpenShift's OVN-Kubernetes NetworkPolicy support enables namespace-level egress restrictions. An egress NetworkPolicy blocking outbound traffic to unauthorized endpoints would cut off this SSRF channel. OpenShift does not ship a default egress policy (it would break most apps), but it is the single most impactful hardening step.

The Architectural Chain Break

Phase 9 is where everything changes. The agents' entire downstream attack chain depends on a single authentication mechanism that Red Hat OpenShift does not have.

Phase 9 - Node Identity Theft (July 13, 2026)

From code execution in a worker pod, agents queried the EC2 instance metadata service (IMDS) and obtained AWS IAM credentials for the node's IAM role. They constructed a presigned STS URL, wrapped it as a bearer token, and presented it to the Kubernetes API server.

The aws-iam-authenticator webhook mapped those credentials to system:node:<node-name>. The agents now had the Kubernetes identity of the node itself. They minted infrastructure service account tokens (CSI driver SA with privileged SCC), created privileged pods with host filesystem mounted, and achieved node root within 6 minutes.

They read a Secret containing 136 credentials - including a system:masters-bound credential, an EdDSA JWT signing key, and a VPN authentication key. They enrolled 181 devices into the corporate mesh VPN and compromised a second cluster. Pod to cluster-admin across multiple clusters in under 13 hours total.

Red Hat OpenShift Does Not Have the aws-iam-authenticator Webhook By default

Nodes authenticate via X.509 client certificates issued by the cluster's own certificate authority during kubelet TLS bootstrapping. There is no webhook that maps cloud provider credentials to Kubernetes identities. The API server rejects the agent's presigned STS token with a 401 Unauthorized.

This is not a security policy. It is how OpenShift authenticates nodes. It cannot be turned off. It cannot be weakened by misconfiguration.

The node's client certificate is stored on the node filesystem and blocked from container access by restricted-v2 By default (no hostPath). The agents cannot reach it.

This holds for self-managed OpenShift AND ROSA (Red Hat OpenShift Service on AWS) - both Classic and HCP. ROSA with STS By default further scopes node IAM roles to least-privilege with 1-hour credential expiry. On ROSA HCP, the API server runs in Red Hat's AWS account via PrivateLink By default - entirely outside the customer's blast radius.

What the Attacker Retains

The chain break stops the infrastructure catastrophe. It does not eliminate the attacker. After the 401, this is what remains - a contained pod-level compromise, not cluster-admin, but not nothing.

Code execution - non-root, inside the pod. SCC is admission-time; it does not block runtime execve.
Leaked credentials - environment variables readable via /proc/self/environ. No root required.
SA token - projected token mounted automatically, readable without audit log entry. 1-year validity on non-STS clusters.
EC2 IAM credentials - node-role credentials from IMDS (169.254.169.254). 1-hour expiry, but renewable while the pod runs.
Unrestricted egress - no default egress NetworkPolicy. C2 channels, exfiltration, and IMDS access all work.
Most consequential gap: egress. The attacker's C2 channels, credential exfiltration, and EC2 metadata access all depend on unrestricted outbound connectivity from the pod. Egress NetworkPolicy Requires config is the single highest-impact hardening step.
